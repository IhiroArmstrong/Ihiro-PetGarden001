## 产品一句话定位

**English**

> Focus Tiger is a mindful companion that helps people practice focus, awareness, and emotional freedom — learning to observe thoughts and emotions without being controlled by them.

**中文**

> Focus Tiger 是一位正念陪伴伙伴，通过专注练习和日常觉察，帮助用户培养专注力、心流能力，并逐渐学会观察情绪，而不是被情绪控制。

**差异化定位（对外沟通参考）**：Focus Tiger 不是又一个番茄钟 App，而是 **AI 时代帮助人类重新训练注意力、觉察力与内在自由的陪伴伙伴**。这句话用于产品战略、品牌叙事和对外文案参考，不要求原样出现在产品 UI 中。

## 市场与语言原则

本项目设计原则上默认面向海外市场，产品默认语言为**英文**。

- 所有新增 UI 文案、交互提示、非模态提醒、错误信息等，必须首先以自然、简洁的英文撰写，并接入 `src/locales/i18n.js` 的 `t()` / `tPool()` 体系。
- 不允许在业务逻辑、UI 组件或交互触发代码中硬编码任何语言的用户可见文案字符串；dev-only 调试工具不属于产品 UI，但不得进入正式用户路径。
- 中文作为可切换的次要语言保留，`src/locales/zh.json` 必须与默认英文 `src/locales/en.json` 保持 key 结构一致并同步更新。
- 产品默认展示、素材命名、标识符，以及代码注释中的示例文案，均以英文为准；文档说明和非用户可见的实现注释可按协作需要使用中文或英文。
- 缺少翻译时应回退默认语言英文，不得以硬编码中文或其它语言绕过字典机制。

## 正念伙伴原则

小老虎的用户心智定位是 **Mindful Companion（正念伙伴）**，不是监督者、老师、教练，也不是需要用户喂养、维持健康或承担照料责任的传统电子宠物。

- 摸头、Boop、眼睛跟随等伙伴式互动可以保留，但面向用户的文案不得采用饥饿、生病、喂养、照料失败或宠物收集叙事；
- 不得暗示「用户不专注 → 小老虎不健康」「用户回来 → 小老虎恢复健康」；
- 长期成长只能表现为共同经历增加、环境细节解锁、获得永久纪念物或新的温和表达，奖励只增不减；
- 产品鼓励 **regular practice, at your own pace**，不得用 `daily practice`、连续签到或断签文案制造每日义务感。

## 诚实机制（Honesty System）

Focus Tiger 允许用户手动补登在其他场景（如其他冥想 App、线下打坐、散步静心等）已完成的专注 / 正念练习。系统对此**无条件相信**，不做任何形式的验证、质疑或「真假练习」判定。

这一原则的价值在于：

- 避免用户因为「这次专注 App 没记录到」而产生挫败感，或被迫重新计时的负担；
- 通过一个简短的**仪式化动作**（而非表单填写）完成补登，保持「陪伴而非监督」的调性；
- 诚实机制下产生的记录，与正常计时完成的记录，在产品体验与数据处理上**一视同仁**，不做区分，也不标记为「次等」。

硬性约束：

- 禁止出现「确定吗？」「请如实填写」「我们无法验证」等验证性 / 怀疑性文案；
- 补登记录不得降低反馈强度、不得排除在当日达标 / 里程碑统计之外（除非另有独立立项并明确说明）；
- 诚实补登是用户**主动发起**的动作，不占用「系统主动提醒」类限频额度（如共享提醒池每日 3 次）；具体交互见 `DESIGN.md`「DORMANT 唤醒仪式（Honesty Check-in Ritual）」。

**会话语境的自主声明（Companion Mode）**：开始专注前由用户声明本次是「留在本页 / 去别处练习 / 多工具间工作」，同属诚实优先于技术猜测——尤其知识工作多工具切换与 visibility「分心」信号无法区分时，**禁止**用标签页可见性对用户做系统性误判。缺陷背景与三选一规则见 `DESIGN.md`「专注会话陪伴模式」与「Focus Confidence」已知设计缺陷。

## 核心成长模型

产品的核心逻辑从「专注时间 → 小老虎陪伴成长」的单线模型，升级为四层递进模型：

> **觉察 Awareness → 专注 Focus → 心流 Flow → 内在成长 Growth（小老虎陪伴）**

- **觉察 Awareness**：注意到当下的呼吸、念头、情绪与注意力变化，不急于判断或控制；
- **专注 Focus**：把注意力温和地带回所选择的对象，以练习的方式增强觉察的稳定性；
- **心流 Flow**：当觉察与专注逐渐稳定，用户更自然地进入投入、连贯而少受干扰的体验；
- **内在成长 Growth（小老虎陪伴）**：成长表现为用户与小老虎共同经历的累积，以及观察念头和情绪而不被其牵引的能力逐渐增强；不表现为角色健康、用户等级或必须维持的进度。

**专注不是最终目标，专注只是训练觉察能力的一种方式。**

这一模型是后续所有功能设计的上位指导原则，包括既有的 `EmotionController`、`MindfulAcknowledge`、`Re-focus Acknowledge`、完成反馈和长期纪念奖励体系。功能不能只优化「专注了多久」，还必须检验它是否帮助用户经历「觉察 → 回归 → 稳定 → 更自由地回应」的过程。

## 核心正念原则：观照者而非情绪本身（I am not the emotion）

这不是独立功能模块，而是贯穿角色状态、情绪反馈、文案和交互节奏的设计准则。小老虎应通过自身表现示范「觉察情绪，但不把自己等同于情绪」：不说教、不打分、不做心理分析，也不替用户解释情绪原因。

### 设计准则一：情绪来了，也会离开

- 所有通过 `EmotionController` 触发的**一次性或响应性情绪反馈**，无论强度高低，都必须形成「触发 → 表现 → 收束」闭环；
- 禁止为了工程实现简单，让角色**无限卡在**兴奋、烦躁、惊讶、委屈等反应表演中；
- `Celebrating`、`MindfulAcknowledge`、`SessionComplete`、`WelcomeBack`、未来 `Re-focus Acknowledge` 等正式产品路径受此约束；
- **回归姿态（2026-07-19 修订）**：正式路径的回归目标是「**类似坐禅的安静坐姿**」（可含微睁眼微笑、张望后的静坐、合十/点头后的安坐等），**禁止**刻板要求每一段动画末帧都必须像素级对齐「默认闭目坐禅 `idle-breathing` 第 1 帧」；
- **序列衔接：CapCut 式叠代（2026-07-20）**：两个 2D 序列**无法自然衔接**时（画幅不同、姿态跳变、末帧与下一序列首帧对不齐、硬切会跳），**必须**用叠代溶解，禁止闪切：
  1. 定格上一序列末帧与下一序列首帧；
  2. 双层透明度交叉淡化（叠代），默认约 **1 秒**（`CAPCUT_DISSOLVE_MS`）；
  3. 溶解完成后再启动下一序列的帧推进（`freezeUntilCrossFadeEnds`）。
  实现见 `SpriteSequencePlayer` 双 `<img>` + `EmotionController._finishOneShot`（一次性 → idle 默认启用）。**2026-08-03**：跨动画短淡入（曾 `MICRO_CROSS_FADE_MS` ≈180ms / dormant 520ms）一律改为 **1s CapCut**；**仅**设计为无需转场的硬切（显式 `crossFadeMs: 0`，如 Idle 闭目↔睁眼弧、gaze 段间）保持不变；
- **不连贯序列（2026-07-19）**：若连 CapCut 溶解仍无法接受，调试路径可播完定格末帧；正式路径优先叠代溶解回落，勿为原则硬切默认闭目呼吸；
- **调试面板验收**：右侧姿态按钮对一次性序列默认 `holdPose`（定格末帧、不自动切回默认闭目）；循环态（idle / sleeping / smiling / halo）照常循环。正式会话路径仍可在业务需要时回落 idle，但视觉上优先遵守上两条；
- **闭目坐禅节奏（2026-07-19）**：默认 `Idle` / 调试「坐禅闭眼」= `idle-breathing`（约 **2.5 fps**）完整 pingpong **×5** → 单次 **眨眼** → 往复（约 1–1.5 分钟一次眨眼）。**禁止**哈欠/张望等 Idle 变体；**禁止**在 idle 上再插 `curiousTilt`（会清零计数）。状态机重复进入 IDLE/FOCUSING 不得重启编排。细则见 `EMOTION_BIBLE.md`；
- **持续态节奏（2026-07-19；2026-07-25 修订）**：长时间循环态（尤其 `Sleeping`）须极缓、安宁，禁止「快进抖动」；`sleeping` 默认约 **2 fps**（cloak-sleep 末帧双拍 pingpong；相对早期 4 fps 仍放慢）。`idle-breathing` 亦宜偏慢；一次性唤醒 / 点头等避免急促卡通；
- **一次性情绪时长（2026-07-19）**：确认/仪式类目标 **3.5–7s**（舒适参考 `dormantWake` ≈5.3s）；轻量 `SessionComplete` **2.5–4s**。不足则放慢 fps、重复可循环段、或正倒放/连贯其它序列。细则见 `EMOTION_BIBLE.md` §1.5 与 `ONE_SHOT_DURATION_SEC`；
- `Sleeping` 等由产品状态机决定的休息模式不属于一次性情绪滞留，仍按其独立进入/唤醒规则运行。

基础坐姿中的稳定呼吸代表「观照者本身」：情绪与念头可以经过，呼吸和觉察仍在。这个反复出现的视觉闭环，是产品对用户潜移默化的核心教学——但其落点是「安静坐禅感」，不是「唯一闭目帧」。

### 设计准则二：观察式，而非定性式

用户可见语言只描述被观察到的现象及其流动，不替用户下判断、贴标签、追问原因或给出未经请求的建议。具体强制规范、双语示例与自检清单见 `EMOTION_BIBLE.md`「语言设计原则：观察式措辞规范」。

本原则是「核心成长模型」中从觉察走向内在成长的具体设计约束：成长不是更用力地控制情绪，而是更清楚地看见情绪、与它保持距离，并选择如何回应。

## 无角色语音原则（Text-only Companion）

系统与用户的一切沟通均通过**文字**呈现（非模态文案条、HUD、可选面板等），**不**使用真人配音，**不**使用 lip-sync / 口型同步动画，**不**引入角色语音功能。

技术上虽存在可行路径（复用既有「图生视频 + 抽帧」为固定文案预生成带语音口型序列，接入 `SpriteSequencePlayer`，无需实时 TTS / 音素对齐），产品仍明确拒绝该路径。

**理由：**

1. **打断感**：真人声音的打断感远高于文字浮现，与「安静陪伴、无所住相」存在根本张力——文字可被用户以自己的节奏「路过式」阅读，声音则是强制性、单向的打断；
2. **文案灵活性**：配音后的固定文案难以低成本修改，会削弱「多变体轮换、灵活调整」的既有优势；
3. **能力覆盖**：无法覆盖含运行时动态内容的模板文案（如用户自行输入的专注意图），功能价值天然打折；
4. **场景冲突**：语音默认开或关都会与需要保持安静的环境（办公室、图书馆等）冲突；再加开关本身也是不必要的复杂度。

**效力**：此为**长期产品原则**，不是「当前不做、以后再评估」的临时状态，也**不得**记入 Backlog 待办。除非未来出现根本性的产品方向调整，否则不再重新讨论角色语音功能。情绪与互动表现仍以视觉动作 + 观察式文字为准（见 `EMOTION_BIBLE.md`）。

## 宁静型游戏化与反馈分级原则

- 禁止强迫签到、红点轰炸、概率抽奖、稀缺倒计时、错失恐惧与街机式亢奋反馈；
- 自主行为的随机节奏用于角色生命感，不等于随机奖励；奖励必须由明确、可解释的练习记录触发；
- 每次完成专注都给予轻量情绪确认；
- 每个自然日首次达标才触发一次完整 `Celebrating`，语义统一为「短暂、温暖、有情感的庆祝」；同日后续完成不重复强庆祝；
- 长期里程碑给予只增不减的纪念奖励，具体规则须另开任务设计。

## 永不消失原则

```
老虎不会离开、不会死亡、不会真正"消失"——DORMANT是它唯一需要用户留意的非专注姿态，
且这个状态本身也是可爱的(打瞌睡而非生病挂水)，不制造愧疚感，
只制造"它在等你"的温和召唤感。
```

## 不制造焦虑原则

任何反映用户健康/专注状态的视觉表现，默认/中性状态必须是情绪中性或温馨的(如休憩、陪伴)，不得设计成可被解读为"退步、失败、被扣分、被惩罚"的负面视觉信号(如失色、变暗、枯萎、悲伤表情等)。正向状态只应表现为"额外惊喜/庆祝"，不应通过制造默认态的负面感受来凸显对比。

默认/中性状态：老虎保持本体固有色（自然原色），呈现趴卧休憩(打盹)姿态，不做负面色彩处理；达标/庆祝状态：本体固有色**不变**，金色光环与表面环境光反射（Rim Light 边缘高光）增强，配合悬浮、金光粒子等庆祝效果。角色本体在任何状态下都不做色相/明度渐变（2026-07-15 视觉原则修正，详见 DESIGN.md「视觉状态」章节）。

## 开发原则

### 原则一：一次只做一个任务

做完充分测试再继续，不要同时改多个模块(3D项目下这条原则更重要，
渲染管线+状态机+动画三者耦合，同时改容易互相踩坑，难以定位问题)。

分阶段开发纪律：**一次只做一个任务**，做完充分测试再继续，禁止跨阶段并行开发。

### 原则二：不提前实现超范围功能

目录结构里不出现"暂不实现"的占位文件/文件夹(如network/)，
需要时再建，避免造成"已有基础实现"的误解。

### 原则三：文件命名规则——路径必须使用英文 ASCII

任何会被代码引用、构建流程处理或纳入 Git 版本控制的文件与目录，其路径都必须满足以下硬性要求：

1. **仅使用英文 ASCII 路径**：文件名与目录名采用小写英文 `kebab-case`（必要时可包含数字，扩展名前的 `.` 保留），单词间使用连字符，例如 `wave-hello/`、`idle-breathing/`、`nod-greeting.png`。
2. **禁止高风险字符**：不得在工具链会处理的路径中使用中文字符、空格、下划线、括号（中英文）、省略号或其它特殊字符。这些字符容易在 Windows、Shell 脚本、CI/CD、压缩包解包及 Git 操作中导致编码或参数解析问题。
3. **规则约束路径而非内容**：`docs/*.md` 正文、代码注释及其它文件内容可以正常使用中文；文档文件名与目录名本身仍受英文 ASCII 与 `kebab-case` 约束。
4. **素材入库前必须先规范命名**：用户上传或提供的原始素材、压缩包及其解包内容若名称不合规，Cursor 在复制、处理或纳入项目目录前必须先重命名，不允许把原始非规范路径保留在项目中。
5. **命名应保留语义**：优先使用准确、可读的英文动作或用途名称，例如「点头致意」命名为 `nod-greeting`，不得以无意义编号替代；翻译不确定时可在清单或文档正文中记录中英文对照，但实际路径仍必须为英文。
6. **适用范围不限于素材**：所有未来新增的素材、资源目录、源代码、脚本、配置及文档文件均受此规则约束。发现历史遗留不合规路径时先记录清单，涉及引用或构建链路的重命名应作为独立任务统一修复，避免只改文件名而遗漏引用。

### 原则四：视觉风格规范

```
条纹色：深金/赭石 #8b6914

强调色：蒲团橙 #b5623a（用于关键 CTA 按钮，如 "Sit with Yin"；原朱红 #8b2e2e 已退役）

```

#### 金色光效分层原则（适用范围，2026-07-17 补充）

- **必须使用外围叠加层、不得烧录进角色帧序列**：仅限需要根据运行时连续变化的游戏状态（如 `FOCUSING` 的 `focusLevel`）动态驱动强度或范围的金色反馈。这类效果的数值来自实时状态，必须保持代码可控。
- **可以直接烧录进源视频或帧序列**：一次性、时长固定、由美术分镜创作驱动的叙事型特效动画，例如 `MilestoneGlow` 的呼吸金光与蝴蝶、`Celebrating` 的舞蹈与小金光、`SessionComplete` 的光环淡出。这类内容与角色的其他肢体动作一样，可以作为预渲染帧的一部分。
- **播放期互斥**：播放这类已烧录光效的叙事动画时，必须临时关闭或归零常规 `FocusVisualizer` / Rim Light 实时叠加，避免两套金光叠加导致过曝；动画播放完并回到坐姿呼吸基底后，再恢复由当前运行时状态决定的常规光效。

#### 光影物理渐进原则（适用范围，2026-07-18 补充）

来源与场景细则见 `LIGHT_PROGRESSION_DESIGN.md`。

- **采纳为通用方法**：状态变化优先用环境光 / 色调 / 透明度的连续过渡表达，而不是弹窗、数字、进度条。所有实现默认基于 **2D DOM/CSS 叠加层**，复用 `IncenseGreeting` / `FocusVisualizer` / `LightProgression` 已有叠层模式，不引入新的渲染技术栈。
- **明确排除**：任何要求「实时 3D 相机控制」「Shader 场景渲染」作为主界面交互的提案，除非未来技术路线再次变更为 3D 主线（当前无此计划），否则一律先翻译成 2D 等效方案再评估，不直接按 3D 方案排期。

**字体**：英文默认使用 `system-ui`；中文切换态使用 Noto Serif SC（标题/引导语）+ Noto Sans SC（数据/按钮）作为中文字体回退。

### 原则五：防挫败感机制（v5.0 简化版）

```
老虎永远不会消失，只有两种可见状态需要用户关心：
  金光渐显(专注中) / 打瞌睡(当日尚未完成任何练习时的 DORMANT)
唤醒门槛必须极低（Honesty Check-in：可忽略提示 + 约 10 秒呼吸引导；
详见 DESIGN.md「DORMANT 唤醒仪式」）
正向反馈要即时、可见、有情感：不是"focusLevel+10%"，
而是"老虎舒展身体，向你点头"
```

### 原则六：老虎是主角，专注体验是主角，数据是配角

```
用户看到的是：老虎今天是自然休憩还是金色庆祝
用户感受到的是：我有没有真正专注过、抓住过这段时间
不做多余的进度条/排行榜/成就墙，除非能证明它真的服务于"专注"这件事本身
```

### 原则七：性能设底线，底线之内放心追求视觉效果（v5.1调整）

```
这个产品没有"飞机大战"那种玩法本身的爽点，3D视觉表现力本身就是核心吸引力，
不应该一上来就为了保性能主动压低品质、束手束脚。

正确的做法是：设一条清晰的底线（中端手机稳定30fps、首屏可交互 < 3秒），
只要没测出问题，就放心往视觉效果上investment；
一旦测出某个效果拖慢了帧率，再针对性优化（先降粒子数/简化shader计算，
最后才考虑模型减面），而不是预先假设"3D效果会拖慢速度"就不敢做。

"首屏加载"这件事本身也不等于"必须加载得快"，而是"必须让用户感知不到在等"——
见下方"首屏Poster过渡"策略，感知加载与真实加载速度是两回事，
不要把两者混为一谈来决定要不要克制视觉效果。
```

### 首屏Poster过渡策略（新增，解决移动端首屏加载敏感的问题）

```
不是简化3D效果来换首屏速度，而是用一张"预渲染截帧"图先撑住首屏：

  1. 从真实Three.js场景离屏渲染一帧（老虎坐禅时的默认自然原色构图），
     导出为静态图片，作为 index.html 里的首屏占位图（<img>直接写在HTML里，
     在JS bundle执行前就能显示，是理论上最快的首屏）
  2. 3D场景在后台正常加载GLB/贴图/shader
  3. 加载完成后，占位图淡出、WebGL canvas淡入，无缝切换

关键约束：这张占位图必须是"真实渲染出来的一帧"，不能是美术另画的示意图，
否则切换瞬间会有肉眼可见的"对不上"，比空白等待体验更差。
```

### 原则八：价值优先于复杂度

任何新功能提议，在正式立项开发前，必须先评估以下三点：

1. 是否为用户带来明确的价值提升？
2. 是否显著增加开发复杂度（新增的技术栈、依赖、需要解决的工程难题）？
3. 是否显著增加长期维护复杂度（未来修改/排查问题的难度、跨模块耦合风险）？

只有当「价值」明显超过「复杂度」总和时，才允许该功能进入开发排期。评估结论应以简短文字形式记录在案（即便是「决定暂不做」的功能，也应记录评估理由），避免半年后项目因持续叠加「看起来不错但复杂度过高」的功能而变得难以维护。

**已应用此原则的历史案例（供参考）**：

- **金牌/成就系统**：价值明确，但涉及持久化存储架构与新 UI 模块，复杂度较高，已记录至 Backlog，暂不纳入当前开发范围。
- **Focus Confidence 多信号模型**：已按此原则拆分为「当前可实现的浏览器原生信号（V1）」与「需要插件/系统权限的信号（长期路线图）」两部分，只将 V1 部分纳入当前开发。

## 正向反馈节制原则

达标类的强反馈效果(如庆祝动画)每日限触发一次,不应因用户多次达标而重复播放,避免正向反馈被过度使用导致体验廉价化,也避免被有意"刷"出高频反馈。
