## 6.1 自动化冒烟测试（最高优先级）

**问题**：现在的回归发现方式是"改完代码 → 用户手工点一遍 → 发现问题 → 报告 →
再改"，测试成本压在用户身上，且永远在改动**之后**才发现问题。SCENARIO_TESTS.md
已经把核心场景写成了可执行的步骤脚本，但目前只用来指导人工测试，没有变成机器
能跑的东西。

**要求**：

| # | 规范 |
|---|---|
| S1 | 从 SCENARIO_TESTS.md 场景 A-D 中挑选 5-8 条**确定性**步骤（不依赖概率触发的部分），转成自动化端到端测试，不要求覆盖全部场景，覆盖主链路即可 |
| S2 | 依赖概率触发的步骤（idle 变体等）不纳入自动化范围，继续走人工测试 + 调试强制触发入口（SCENARIO_TESTS.md 已有此要求） |
| S3 | 每次回归锁收尾（N6）前，Agent 必须先跑一遍自动化冒烟测试，测试不过 → 不得声称「已修好」（并入现有 N5 门禁，不是新增独立门禁） |
| S4 | 自动化测试新增/修改后，同步更新 SCENARIO_TESTS.md 对应场景，注明「此步骤已自动化，见 tests/xxx」，避免人工脚本和自动化脚本各自为政、逐渐失配 |
| S5 | 每次「用户报告的 bug 经确认修复」（不限于门闩类），默认追加一条自动化回归用例；确实无法自动化的，才降级为 TEST_TRACKER 人工锁路径——这条是对原文档 N3 的扩展，原文档只要求门闩类行为写失败用例，范围划窄了，容易漏掉其它类型的回归 |

### Cursor Prompt（S1-S4，最高优先级，建议立即执行）

```
请把 SCENARIO_TESTS.md 场景 A-D 转成自动化端到端冒烟测试，纳入常规 CI/本地
测试流程：

1. 先检查项目现有测试框架配置（是否已有 Playwright / Cypress / Vitest 之类的
   e2e 测试基础设施），如果没有，先给出技术选型建议，不要直接引入新依赖。
2. 从场景 A（Kelly 的第一个早晨）、场景 B（Recover）、场景 C（中途主动结束）、
   场景 D（Honesty Check-in）中，挑选不依赖概率触发的确定性步骤，各自转成一条
   自动化测试用例，覆盖主链路即可，不追求覆盖全部细节分支。
3. 概率触发的步骤（idle 变体等）不纳入这批自动化范围。
4. 在 DEV_WORKFLOW_QUALITY.md 的回归锁收尾门禁（N6）前，插入"先跑自动化冒烟
   测试，不过不得声称已修好"这一步，更新规则文件 
   `.cursor/rules/focus-tiger-regression-lock.mdc` 保持一致。
5. 测试写完后，回头更新 SCENARIO_TESTS.md 对应场景步骤，注明已自动化及测试
   文件路径。
6. 完成后给出：新增了几条自动化用例、覆盖了哪些场景步骤、还有哪些确定性步骤
   因技术原因未能自动化（如有，说明原因）。
```

## 6.3 一键清空本地状态（开发环境调试工具）

**问题**：DORMANT、每日提醒额度、hints-seen、intentions 等大量状态依赖
localStorage 和日期判断。测试时经常因为"上次测试留下的脏状态没清干净"产生
"看起来像 bug、其实是状态没重置"的假象，浪费排查时间。

**要求**：

| # | 规范 |
|---|---|
| L1 | 开发环境 debug 面板新增一个"重置全部本地状态"按钮，一键清空项目所有 localStorage key（不是逐个手动清），仅在开发环境可见，不得出现在生产构建 |
| L2 | 点击后应刷新回到全新用户的初始状态（等同场景 A 开局），方便反复复现"新用户第一次打开"这类场景 |
| L3 | DEV_WORKFLOW_QUALITY.md 第 4 节注意事项 3（"测不到新改动优先怀疑测错步骤"）补充一条：先用这个重置按钮排除"脏状态"这个可能性，再怀疑其它原因 |

### Cursor Prompt

```
在开发环境 debug 面板新增"重置全部本地状态"按钮：
1. 点击后清空项目所有 localStorage key（列出当前项目实际使用的全部 key，
   不要遗漏，包括但不限于 intentions.v1、reflections.v1、hints-seen.v1、
   companion-mode.v1、当日完成记录等）。
2. 清空后自动刷新页面，回到等同"全新用户首次打开"的状态。
3. 仅在开发环境可见，确认生产构建不包含这个入口。
4. 更新 DEV_WORKFLOW_QUALITY.md 第 4 节，补充"测不到新改动时先用此按钮排除
   脏状态"这条注意事项。
```

## 6.5 汇报必须单独列出"待你决定 / 待你知道"清单

**问题**：2026-07-20 冒烟测试整合汇报中，"是否引入 Playwright""controller 级
覆盖 vs 视觉/序列层完全未覆盖""人工测试项到底是 1 行还是 6 行"这几件事，都是
应该被用户明确知道甚至拍板的事项，但全部被写进了叙述性段落里，没有在末尾单独
成一份清单，容易造成"看起来都做完了"的错觉。

**要求**：

| # | 规范 |
|---|---|
| P1 | 每次任务汇报，末尾必须有一个独立小节，标题固定为「待你决定 / 待你知道」，不得省略，哪怕内容是"无" |
| P2 | 该清单至少覆盖三类：①需要用户拍板的技术/产品决策（如是否引入新依赖、是否接受某个范围妥协）②本次覆盖范围之外、仍需人工验证的具体子项（逐条列出，不得汇总成模糊的"1项""若干项"这类表述）③明确推迟、但没有具体触发条件的事项，需注明"后排，等 XXX 时机再提"或"无限期搁置，如需可随时要求" |
| P3 | 正文叙述中提到的"待拍板""以后再说""仍需人工"等表述，必须同步出现在这个清单里，不能只在正文出现一次就算交代过了 |

### Cursor Prompt

```
在 DEV_WORKFLOW_QUALITY.md 第 3.3 节"收尾（回复用户前）"的完工门禁清单中，
新增一条硬性要求：

- [ ] 回复末尾包含独立的「待你决定 / 待你知道」小节，逐条列出：
  1) 需要用户拍板的技术/产品决策
  2) 本次未覆盖、仍需人工验证的具体子项（逐条列出，不得汇总成模糊的"1项"
     "若干项"这类表述）
  3) 明确推迟且暂无具体触发条件的事项

这条要求写入 N6 附近（回归锁收尾）或单独编号为 N12（如 N12 已被占用则顺延），
同步更新 .cursor/rules/focus-tiger-regression-lock.mdc，确保这不是文档里的一句话，
而是每次收尾汇报的强制检查项。

回顾 2026-07-20 冒烟测试整合的汇报，按这条新规范重新整理一份"待你决定/待你
知道"清单补发给用户，逐条列出：
- 是否引入 Playwright（当前搁置，需何种条件下再议）
- controller 级冒烟未覆盖视觉/序列层（睡着切换、Arrival气泡时长、Ambient、
  真实切页60s、Celebrating动画、桥接后完整Arrival UI）——请拆成 TEST_TRACKER
  里的独立行，不要合并成一行
- 6.3/6.4 后排事项的触发条件（用户主动要求，还是有其它触发时机）
```

## 6.4 共享资源对照表（识别高风险面的辅助工具）

**问题**：现有高风险面清单（§2.3）是手工从事故里总结出来的静态列表，遇到新的
改动时，全靠记忆判断"这算不算高风险"，没有系统性的识别方式。

**要求**：

| # | 规范 |
|---|---|
| R1 | 维护一份简单对照表：`EmotionController` / `IdleOrchestrator` / 各 localStorage key 分别被哪些功能/场景共用，touch 到共享资源前先查这张表，而不是单靠印象判断影响面 |
| R2 | 这张表和 §2.3 高风险面清单是互补关系，不是替代——§2.3 列的是"已知踩过坑的具体点"，这张表列的是"当前所有共享资源分别被谁用"，帮助发现§2.3 还没覆盖到的新风险点 |
| R3 | 每次新增一个 emotion key、localStorage key，或者往 IdleOrchestrator 变体池加东西时，顺手往这张表补一行，成本很低，不需要专门排期维护 |

### Cursor Prompt

```
在 ARCHITECTURE.md 或新建 SHARED_RESOURCES.md 中，建一张共享资源对照表：

1. 列出当前项目里 EmotionController 的所有 emotion key、IdleOrchestrator
   的所有变体、以及全部使用中的 localStorage key。
2. 每一行标注：这个资源被哪些功能/组件/场景使用（不需要非常详尽，够判断
   "改这个会不会波及别的功能"即可）。
3. 这张表和 DEV_WORKFLOW_QUALITY.md §2.3 高风险面清单不是一回事，是互补
   工具，不要合并成一张表。
4. 以后新增 emotion key / localStorage key / idle 变体时，要求顺手补一行，
   写进 DEV_WORKFLOW_QUALITY.md 相关规范里（可以作为 N11 的补充说明）。
```
