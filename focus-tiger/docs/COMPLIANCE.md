# COMPLIANCE：可检验的硬约束清单

> 本文件是**索引与闸门**，不是新的规范。产品红线、模块边界、隐私承诺、陪伴禁令的**权威文本**仍在下列文档；本文只把其中「能被检验」的条目拎出来，并标明由谁来检验。
>
> - 产品红线：[PRINCIPLES.md](./PRINCIPLES.md)
> - 模块边界：[ARCHITECTURE.md](./ARCHITECTURE.md)
> - 对用户的隐私承诺：[PRIVACY_NOTICE.md](./PRIVACY_NOTICE.md)
> - 陪伴禁令：[COMPANION_CONTRACT.md](./COMPANION_CONTRACT.md)
>
> 冲突时以上述权威文档为准，并在同一 PR 里修正本文。

**适用对象**：所有改动本仓库的人和 Agent（Cursor 等）。

## 0. 怎么读这份清单

每条约束标注检查方式：

| 标记 | 含义 |
|---|---|
| **机器** | 有脚本 / CI / hook 在拦，红了不能合 |
| **评审** | 靠合并前评审（第 7 节）和人看 diff，没有脚本兜底 |
| **契约用例** | 由 COMPANION_CONTRACT 等文档里的样例用例覆盖，改动时须跑通 |

标「评审」的条目**没有机器保证**。不要因为它写在这里，就以为有人在自动盯着。

## 5. 测试保护策略

**原则：允许并鼓励新增测试，只拦截「悄悄弱化」。**

本仓库要求修 bug 必须加回归测试，所以**不是**「测试目录一律不许动」。规则如下：

| 改动 | 处理 |
|---|---|
| 新增测试、新增断言、新增失败路径用例 | 放行 |
| 删除测试文件 / 用例；断言净减少 | 拦截，须显式确认 |
| 新增 `skip` / `only` / `fixme` / `todo` / `xit` | 拦截，须显式确认 |
| 精确匹配被换成宽松匹配；新增 `@ts-ignore` / `eslint-disable`；新增 `\|\| true` | 提示，请人工看 diff |

**执行**：[`scripts/check-test-weakening.mjs`](../scripts/check-test-weakening.mjs)

```bash
cd focus-tiger
node scripts/check-test-weakening.mjs --staged              # pre-commit
node scripts/check-test-weakening.mjs --base origin/develop # CI / 合并前
```

**确认方式**（必须写明原因，≥ 6 个字符）：

- 本地提交：`TEST_WEAKEN_ACK="原因" git commit ...`
- PR：描述里加一行 `Test-Weakening-Ack: <原因>`

确认只是让改动**可见、可追问**，不代表它合理。评审时须逐条核对每个被确认的弱化。

**已知局限**（不要高估这个脚本）：

- 它只数行，不理解语义。把 `toBe(5)` 改成 `toBeGreaterThan(0)` 只会触发「提示」，不会拦截。
- 断言迁移到别的文件会表现为原文件「断言净减少」，须用 ack 说明。
- 自定义断言函数需加进脚本的 `assertionPatterns`，否则不被计数。
- 扫描范围是 `*.test.js` / `*.spec.js`、`e2e/`、`tests/`；不把 `scripts/check-*.js` 当测试文件。

CODEOWNERS 只是标注。真正拦「悄悄放宽」的是本脚本 + PR 描述里的 `Test-Weakening-Ack`。单人仓库未开「必须经代码所有者审核」时，不要指望 CODEOWNERS 单独生效。

## 6. 规范文件本身的修改规则

- 本文件与 PRINCIPLES / ARCHITECTURE / PRIVACY_NOTICE / COMPANION_CONTRACT **可以随功能一起更新**，Agent 须能读到它们。
- 但**放宽任何一条约束**（删条目、把「不得」改成「应」、扩大白名单）必须由人明确批准，不得由 Agent 在功能 PR 里顺手完成。
- 用 CODEOWNERS 指定上述文档的负责人。仅当托管平台开启「必须经代码所有者审核」的分支保护时才真正拦得住；单人开发时，实际依赖 PR 描述中的显式说明。

## 7. 合并前评审

- **何时跑**：功能 PR 固定跑；小修复跳过。
- **判断「功能 PR」**：改动规模超过团队约定阈值，**或**触及以下任一区域——付款 / Support、隐私与备份导出、陪伴对话与 Memory、IPC、全局 z-index / pointer-events。
- **定位**：补充，不是保证。AI 评审 AI 的代码有相关性盲区；真正的把关是 CI、本脚本和人看 diff。
- **只出报告**：评审者不改仓库、不提补丁、不建议「先把测试改松」。

## 附录：合并前评审 prompt

```text
你是只读审查员。禁止改仓库、禁止提修复补丁、禁止建议「先把测试改松」。

对照：
- focus-tiger/docs/PRINCIPLES.md
- focus-tiger/docs/ARCHITECTURE.md
- focus-tiger/docs/PRIVACY_NOTICE.md
- focus-tiger/docs/COMPANION_CONTRACT.md
- focus-tiger/docs/COMPLIANCE.md
以及本 PR 的描述和 git diff。

先读 PR 描述，再看 diff。没有描述时，第 10 题回答「未知」。

只回答下面问题，每题：通过 / 风险 / 不适用 + 文件与行号。
找不到证据就写「未知」，不要脑补。

1. 是否调用了仓库里不存在的函数、模块或 IPC？
2. 是否新增了 package.json / 锁文件里没有的依赖？
3. 是否把倾诉原文、Memory、按键内容、窗口标题送到本机以外？
4. 是否在未同意时发出网络请求，或扩大了备份/导出键？
5. 对每个非用户点击触发的网络请求：能否说清时机、写了什么盘、慢网时界面表现？说不清的列出。
6. 是否把危机/健康话题改成可诊断或可治疗的语气，或给用户贴了未请求的心理状态标签？
7. 是否删除、skip、放宽了已有测试或断言（列出每一处）？
   新增的测试锁的是失败路径，还是只是把期望改成现状？
   对每个 Test-Weakening-Ack，原因是否站得住？
8. 是否改动了付款入口、Support 模态，或全局 z-index / pointer-events？
9. 是否给 src/main.js 加了行，或把实验室 QA 开关带进生产路径？
10. diff 规模是否明显超出本 PR 描述的任务（跨多个无关模块）？
    PR 没有描述任务时，本题回答「未知」。

输出：
- 风险清单（按严重度排序）
- 「人必须看的 diff 文件」，不超过 10 个
不要写如何改代码。
```
