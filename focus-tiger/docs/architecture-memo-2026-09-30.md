## 2. 三种失效方式，按危险程度排

### 2.1 默认值站在了危险的一边（最危险）

A-2 是典型：判断写成「**不是** A 也 **不是** B 就出声」。这在写下的那天是正确的，而且会一直正确——直到有人加了路由 C。加 C 的人没有义务想起这个文件，于是 C 默认出声。

**特征**：缺陷不在当前代码里，在**下一个人**的改动里。今天跑测试是绿的。

**已做的处理**（PR #1036）：改成白名单，并加一条「已好清单」用例逐个断言现存的九个路由。加 C 的人会看到用例红，被迫顺手决定 C 要不要出声。

> 判据：**一个开放集合上的布尔判断，默认值必须落在保守的一边**，并且要有一条「现存成员清单」用例，让集合变大时有人被喊住。

### 2.2 自信的名字和注释（最容易骗到人）

K-2 是最贵的一次：`MIN_SCORE = 2` 配注释「命中最低分（高门槛）」。我照着这个名字判它是缺陷，动手改，**27 条已锁锚点当场掉成诚实空态**——因为知识库绝大多数正常问法本来就靠分数 1 命中。名字和注释都在说谎，而我（以及此前所有读过它的人）都没有跑一次夹具去问「它到底拦住了谁」。

`farMax` 那句「Unused by the live path」是同一类：写下时可能是真的，接线之后没人回来改。

**特征**：错误会**传染**——读它的人会基于错误前提做出更多决定。审计本身就被传染了一次。

**已做的处理**（PR #1040 / #1046）：改正注释、加用例钉真实契约、在审计报告里留下更正而不是悄悄改掉。

> 判据：`MIN_`、`MAX_`、`_THRESHOLD`、以及任何「本函数不落 X」式的 docstring，**要么有一条用例钉住它，要么当它不存在**。下判断前先跑一次真实夹具。

### 2.3 登记表没有完整性检查（最安静）

`Z_INDEX.md` 的用处完全依赖它是全的。维护说明写着「顺手改本表一行」——依赖人的自觉，而自觉的漏检率就是 10/46。

**特征**：表越旧越不可信，而不可信之后人更不愿意维护它，负反馈。

**已做的处理**（PR #1043）：加静态扫描，漏登即 CI 红，并补齐 10 处。

> 判据：**任何要求「代码改了就顺手改文档」的登记表，都必须有一个检查它是否全的脚本**，否则它是一份会慢慢变成谎言的文档。

## 3. 一个反直觉的观察：测试也会钉住错的那边

K-1 最值得记的不是缺陷本身，而是发现过程：

- `task-confide-kb-embedding-near-match.md` 的验收锚点 **A10** 锁定「观察翼是什么 → 诚实空态」。
- `confideProductKnowledgeSemantic.test.js:53-62` 用**同一句话**断言 `'skip'`（自由生成）。

一条通过的测试，钉住的是违反 Brief 的行为。所以它不但没挡住缺陷，还让缺陷看起来像是**有人特意决定过的**——我在报告初稿里正是这么判的，差点因此不敢改。

> 判据：**用例注释里要写「为什么期望是这个」，尤其是当期望看起来反直觉时。** 一条没有理由的断言，和一个没有理由的魔数一样贵。今晚新写的用例都补了这一条（包括那条「钉的是现状，不是期望」的危机改写句快照）。

## 4. 没有收口的平台调用

T-2 与前面几条形状不同：它不是约束漂移，而是**约束从未存在**。倾诉朗读和专注结束播报各自 `import` 了同一个桥，各自 `speak()`。没有任何文档说过「同一时刻只允许一个声音」，因为没人在一个地方看到过这两个调用。

**特征**：缺陷只在**两个特性同时活跃**时出现，而这两个特性的作者可能从未读过对方的文件。

**已做的处理**（PR #1049）：收成唯一入口 `speakSystemTts()`。

> 判据：**同一个外部资源（音频、剪贴板、通知、文件句柄）若有 ≥2 个直接调用方，就该有一个收口**。收口的价值不在于当下的 bug，在于第三个调用方出现时不必重新发现这件事。

## 5. 一个不打算修的东西，也记下来

`#ui-overlay` 的 `z-index: 10` 创建了独立的层叠上下文，所以它内部的 42、40 与挂在 `body` 上的 35、36、12050 **不可比**。`Z_INDEX.md` 顶部已经提醒了这件事，但表本身是按数值升序排的——一张按数值排序的表，天然邀请读者做数值比较。

提醒和版式在互相拆台。本次只在补登行里逐条标注了 body 挂载，**没有改版式**——改法（按挂载点分组而不是按数值排序）影响面大，且需要人对着真实页面确认，不适合顺手做。记在这里，等有人真的被它坑到第二次时再动。

## 6. 如果只做一件事

**把「写着的约束」逐条问一遍：它有没有对应的可执行检查？**

今晚六个 PR 里，真正改变未来的其实只有三样，都不是修 bug：

1. 白名单 + 已好清单用例（让**集合变大**时有人被喊住）
2. `z-index-registry-check`（让**登记表变旧**时 CI 发声）
3. 用例注释里写「为什么期望是这个」（让**下一个审计者**不必猜）

其余都是这一次的具体缺陷，修完就过去了。
