# Task Brief B1 — 架构与代码质量审计

- 所属基准：`AUDIT_BASELINE.md` v1.1
- 负责维度：① 架构（12%）、② 代码质量（12%）
- 建议执行方式：独立新会话，一个会话只做本 Brief
- 输出目录：`docs/audit/findings/<日期>/`

## 1. 目标

评估当前架构是否支撑产品继续增长（功能持续增加、多语言、本地 AI、数据备份/上传），代码质量与可维护性是否可持续；找出结构性问题，给出可执行的改善措施与计划。

## 2. 范围

**纳入：**

- 全部前端/运行时代码（Lit / 原生 ES Module）、本地 AI 相关模块、Confide 与路由仲裁、数据存储与备份、叠层 UI 体系
- 构建、打包、依赖结构
- 代码规范、PR 规模与提交习惯

**不纳入：**

- 具体 UI 视觉与欧美文案（见 B4a）
- 安全与隐私细节（见 B5）
- AI 输出质量（见 B6）

## 3. 输入

- `docs/audit/AUDIT_BASELINE.md`（必须先通读）
- `docs/audit/facts/<日期>/`（第 0 轮。若缺失，先列缺口，必要时补取证并写入 `facts/`）
- 仓库全部源码、`docs/`、PR 记录、CI 配置、任务账（TASKS / TEST_TRACKER）

## 4. 检查清单

### A. 架构

- [ ] **决策可追溯**：关键架构决策能否在 `ARCHITECTURE.md`、`PRINCIPLES.md`、`PROCESS.md`、合并说明中追到？矛盾点列出。
- [ ] **（可选）** C4 Context / Container / Component：若绘制，须标注与代码不一致处；**未画不扣分**，记「方法未采用」即可。
- [ ] 模块边界：分层是否清晰？跨层引用、循环依赖？（附依赖图或违规清单）
- [ ] 核心状态与数据流：用户状态、练习记录、成长度量、Yin 状态存储与读写入口是否集中、可理解？
- [ ] 多个「仲裁/路由/契约」体系之间是否职责重叠或冲突？
- [ ] **（可选）** ADR：无独立 ADR 目录时，用「权威文档 + PR」映射表代替；**不**因缺少 ADR 文件名而判不过线。
- [ ] 架构约束是否有自动化检查或 CI 守门？列出已有与缺失。
- [ ] 数据 schema 版本与迁移机制：升级后旧数据是否安全？
- [ ] 扩展性与复杂度趋势：构建体积、测试时长（引用事实底稿或自跑命令）。
- [ ] 按 ISO/IEC 25010 可维护性 / 可移植性 / 兼容性：**仅对已检子项**给分。

### B. 代码质量

- [ ] lint / 类型检查 / 格式化：结果与豁免清单
- [ ] 复杂度：圈复杂度、函数/文件行数 Top 清单（工具可复现）
- [ ] 重复代码与死代码
- [ ] 命名、注释、文件组织；中英文混用情况
- [ ] 错误处理：吞异常、空 catch、未处理 Promise
- [ ] 全局状态、魔法数字、硬编码文案/URL/密钥
- [ ] 依赖：数量、许可证、体积贡献 Top 10
- [ ] PR 管理：近若干 PR 的规模分布与可审性
- [ ] 技术债：分级与估算（SQALE 思路，可选）
- [ ] AI 生成代码特有风险：重复实现、与契约不一致

## 5. 输出格式

产出文件：`docs/audit/findings/<日期>/B1-architecture-code-findings.md`。

评分表须含「检状态」列（已检 / 部分已检 / 未检）。**未检不得填 0–4 分**。

含：`## 3.1 补充产出` —— 可选 C4 图、依赖违规清单、建议的新增守门清单、技术债表。

## 6. 证据要求

除 `AUDIT_BASELINE.md` 第 6 节外：

- 依赖/架构问题：附工具原始输出（工具名 + 命令）
- 「模块边界违规」：给出 import 链路径

## 7. 通用规则

1. 只读审计：仅写入 `docs/audit/facts/` 与 `docs/audit/findings/<日期>/`。
2. 发现格式与分级见 `AUDIT_BASELINE.md`。
3. **未检**与证据不足分开写；未检**不打分**。

## 8. 完成标准（Definition of Done）

- [ ] 两个维度均有「检状态」说明；已检部分有过线与否依据
- [ ] 未检子项与下一步取证写清
- [ ] 所有 P0/P1 有路径级证据或明确「未检」
