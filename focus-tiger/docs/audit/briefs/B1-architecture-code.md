# Task Brief B1 — 架构与代码质量审计

- 所属基准：`AUDIT_BASELINE.md` v1.0
- 负责维度：① 架构（12%）、② 代码质量（12%）
- 建议执行方式：独立新会话，一个会话只做本 Brief
- 输出目录：`docs/audit/findings/<日期>/`

## 1. 目标

评估当前架构是否支撑产品继续增长（功能持续增加、多语言、本地 AI、数据备份/上传），代码质量与可维护性是否可持续；找出结构性问题，给出可执行的改善措施与计划。

## 2. 范围

**纳入：**
- 全部前端/运行时代码（Lit / 原生 ES Module）、本地 AI 相关模块、Confide 与路由仲裁、数据存储与备份、叠层 UI 体系
- 构建、打包、依赖结构
- 代码规范、PR 规模与提交习惯

**不纳入：**
- 具体 UI 视觉与文案（见 B4）
- 安全与隐私细节（见 B5）
- AI 输出质量（见 B6）

## 3. 输入

- `docs/audit/AUDIT_BASELINE.md`（评分标准、分级、证据要求、发现格式——必须先通读）
- `docs/audit/facts/<日期>/`（第 0 轮"事实底稿"。若目录不存在或缺少你需要的数据，先在报告中列出缺口，再自行用工具补取，并把原始输出存入该目录）
- 仓库全部源码、`docs/`、Epic / Issue / PR 记录、CI 配置

## 4. 检查清单

### A. 架构
- [ ] 绘出当前 C4 的 Context / Container / Component 三层图（Mermaid 文本即可），标注与代码实际是否一致
- [ ] 模块边界：是否有清晰的分层？有无跨层直接引用、循环依赖？（附依赖图与违规清单）
- [ ] 核心状态与数据流：用户状态、练习记录、成长度量、Yin 状态的存储位置与读写入口是否唯一？
- [ ] 多个"仲裁/路由/契约"体系（分散仲裁、Confide 路由、叠层 UI 契约、记住—响应读层、Commitment-Timing 等）之间是否职责重叠或相互冲突？
- [ ] 架构决策可追溯性：关键决策是否有 ADR 或等价文档？文档与代码是否一致？
- [ ] 架构约束是否有自动化检查（适应度函数）？列出已有与缺失
- [ ] 数据 schema 版本与迁移机制：升级后旧数据是否安全？
- [ ] 扩展性与复杂度趋势：功能数量增长对构建体积、启动时间、测试时长的影响
- [ ] 按 ISO/IEC 25010 的可维护性 / 可移植性 / 兼容性子特性逐项给出判断

### B. 代码质量
- [ ] lint / 类型检查 / 格式化：结果与豁免清单（被禁用的规则及原因）
- [ ] 复杂度：圈复杂度、函数/文件行数 Top 20 清单
- [ ] 重复代码与死代码：比例与 Top 清单
- [ ] 命名、注释、文件组织的一致性；中英文混用情况
- [ ] 错误处理：是否有吞异常、空 catch、未处理 Promise
- [ ] 全局状态、魔法数字、硬编码文案/URL/密钥
- [ ] 依赖：数量、版本、更新频率、许可证、体积贡献 Top 10
- [ ] PR 管理：近 50 个 PR 的平均规模、评审与合并方式、提交信息规范
- [ ] 技术债：按 SQALE 思路分级，估算偿还成本
- [ ] AI 生成代码特有风险：重复实现、过度抽象、未使用的兼容层、与既有契约不一致

## 6. 证据要求

除 `AUDIT_BASELINE.md` 第 6 节通用要求外，本 Brief 特别要求：

- 依赖/架构问题：附依赖分析工具的原始输出（工具名 + 命令）
- 复杂度/重复/死代码：附工具报告路径，列出的清单须可由命令复现
- 每条"模块边界违规"至少给出 import 链的完整路径

## 7. 通用规则

1. 只读审计：**不得修改产品代码**。唯一允许写入的位置是 `docs/audit/facts/` 与 `docs/audit/findings/<日期>/`。
2. 每条发现按 `AUDIT_BASELINE.md` 第 7 节格式书写，级别按第 5 节定义，证据按第 6 节要求。
3. `事实 / 推断 / 建议` 分开标注；无证据的结论标 `[假设]` 并写验证方法。
4. 不重复审查已有专项治理的部分：只审"该治理机制是否仍在运转、是否被绕过"，并引用其既有文档。
5. 不得因为"看起来合理"而给高分；无法取得证据的检查项，得分按"证据不足 = 最多 2 分"处理，并写明缺什么证据。
6. 发现 P0（含否决项）时，立刻在输出文件顶部以 `🚩` 标出，不要等到最后。
7. 同一问题跨维度出现时，只在最相关的 Brief 中登记，其余用"见 Bn-xx"引用。
8. 对每个负责的维度，给出 0–4 分评分、评分理由，以及"距离通过线还差什么"。
9. 最后附"本次审计的盲区与局限"（哪些结论需要真人验证、哪些需要运行时数据）。

## 8. 完成标准（Definition of Done）

- [ ] 两个维度均有评分、理由与差距说明
- [ ] C4 图与适应度函数建议已产出
- [ ] 所有 P0/P1 发现都有路径+行号证据
- [ ] 已列出与事实底稿的数据缺口
