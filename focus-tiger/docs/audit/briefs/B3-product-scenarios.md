# Task Brief B3 — 产品功能与场景审计

- 所属基准：`AUDIT_BASELINE.md` v1.0
- 负责维度：⑤ 产品功能与场景（12%）
- 建议执行方式：独立新会话，一个会话只做本 Brief
- 输出目录：`docs/audit/findings/<日期>/`

## 1. 目标

评估产品功能是否围绕清晰定位、核心场景能否端到端完成、功能之间是否冲突或过度堆叠，并判断功能组合对欧美笔记本电脑用户是否有清晰价值。

## 2. 范围

**纳入：**
- 全部用户可见功能与入口（专注、Yin 陪伴、Confide、冷启动目标/今日方向、Ground Exercise、成长旅程、艺术收藏、语音指令、研究共修、引导冥想等）
- 场景文档（SCENARIO_TESTS 等）与实际行为的一致性
- 商业化相关入口（付费、订阅、备份）

**不纳入：**
- UI 视觉细节与可访问性（见 B4）
- 代码质量（见 B1）

## 3. 输入

- `docs/audit/AUDIT_BASELINE.md`（评分标准、分级、证据要求、发现格式——必须先通读）
- `docs/audit/facts/<日期>/`（第 0 轮"事实底稿"。若目录不存在或缺少你需要的数据，先在报告中列出缺口，再自行用工具补取，并把原始输出存入该目录）
- 仓库全部源码、`docs/`、Epic / Issue / PR 记录、CI 配置

## 4. 检查清单

- [ ] 产品定位一句话：从代码与文案中反推出来，并与项目文档的定位对照是否一致
- [ ] 功能清单：列出全部功能、入口、首次出现位置、使用频次假设
- [ ] 核心场景（至少 5 个）端到端走查：新用户首次启动 / 开始一次专注 / 专注中被打断 / 情绪低落求助 / 回访与成长 / 备份恢复
- [ ] 每个场景给出：步骤数、卡点、异常/空状态处理、退出路径
- [ ] 功能冲突与重叠：同一用户意图是否有多个入口或多套逻辑？（如恢复类功能与接地练习、多个提醒/陪伴触发源）
- [ ] 功能密度：新用户首次看到的入口数量；是否存在"功能多但价值路径不清"
- [ ] 打扰与克制：主动触发（提醒、陪伴、吹花日等）频率与可关闭性，是否会与"专注"定位相悖
- [ ] 价值闭环：用户做了什么 → 得到什么反馈 → 为什么会回来
- [ ] 商业化一致性：付费边界是否清晰、是否破坏核心体验
- [ ] 与竞品（至少 Forest、Centered、Flow、Opal 等 3–5 个）的功能对标：差异化是否在产品内被感知到
- [ ] 欧美笔记本用户视角：哪些功能依赖本地文化/语境，哪些在欧美语境下可能难以理解
- [ ] 场景文档与实现是否一致：抽查 10 条场景

## 6. 证据要求

除 `AUDIT_BASELINE.md` 第 6 节通用要求外，本 Brief 特别要求：

- 场景走查须写出可复现的操作步骤与所用环境
- 竞品信息须标注来源与日期；无法验证的标 `[假设]`
- 所有"建议删除/合并"须说明依据，并标注"需真人验证"

## 7. 通用规则

1. 只读审计：**不得修改产品代码**。唯一允许写入的位置是 `docs/audit/facts/` 与 `docs/audit/findings/<日期>/`。
2. 每条发现按 `AUDIT_BASELINE.md` 第 7 节格式书写，级别按第 5 节定义，证据按第 6 节要求。
3. `事实 / 推断 / 建议` 分开标注；无证据的结论标 `[假设]` 并写验证方法。
4. 不重复审查已有专项治理的部分：只审"该治理机制是否仍在运转、是否被绕过"，并引用其既有文档。
5. 不得因为"看起来合理"而给高分；无法取得证据的检查项，得分按"证据不足 = 最多 2 分"处理，并写明缺什么证据。
6. 发现 P0（含否决项）时，立刻在输出文件顶部以 `🚩` 标出，不要等到最后。
7. 同一问题跨维度出现时，只在最相关的 Brief 中登记，其余用"见 Bn-xx"引用。
8. 对每个负责的维度，给出 0–4 分评分、评分理由，以及"距离通过线还差什么"。
9. 最后附"本次审计的盲区与局限"（哪些结论需要真人验证、哪些需要运行时数据）。

## 8. 完成标准（Definition of Done）

- [ ] 评分与差距说明
- [ ] 功能清单表与 5 个场景走查完成
- [ ] 竞品对标完成
- [ ] 所有产品方向类结论已标注"待真人验证"
