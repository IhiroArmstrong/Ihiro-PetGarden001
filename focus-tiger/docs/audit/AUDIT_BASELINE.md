# AUDIT_BASELINE.md — 项目与产品审计基准

- 版本：**v1.1**（2026-11-06）
- 适用范围：Focus Tiger 仓库内全部项目、产品与工程管理（用户可见产品名 **Samatia**）
- 用途：每次审计的统一「尺子」。审计者（人或 AI Agent）按本文件打分、出具发现、制定整改计划
- **本基线审计的定位**：建立可复用的**基线**与证据包。**不是**发布审批；评分卡**不得**输出「可发布 / 不可发布」类结论（见第 11 节）
- 基准本身需要迭代：每次审计结束时更新文末「修订记录」

---

## 1. 审计原则

1. **证据驱动**：每条发现必须带证据（文件路径 + 行号 / 复现步骤 / 命令输出 / 截图）。无证据的只能标为「假设」。
2. **先工具，再判断**：先取得客观数据（静态分析、依赖扫描、覆盖率、同意与网络请求对照、密钥扫描等），再做判断。
3. **三类内容分开写**：`事实`（可验证）/ `推断`（基于事实的判断）/ `建议`（要做什么）。不得混写。
4. **分级而非罗列**：统一使用 P0–P3，并标注修复成本与影响面。
5. **审「治理是否仍有效」，而非从头重审**：已有专项治理的部分（如 e2e 分类治理、叠层 UI 契约、成长度量、Confide 路由评测分层），审查其机制是否仍在运转、是否被绕过。
6. **闭环到任务账**：每条 P0/P1 应能对应到 **任务账条目**（`TASKS.md`、验收记录、`TEST_TRACKER.md` 等）或 Issue；审计会话**只读**，**不得**为凑闭环而当场开新票。登记由**文档治理 / 治理会话**负责（见 `WORKFLOW.md` 与队列治理说明）。
7. **承认 AI 审计盲区**：真实用户行为、留存、真实设备体感无法由单次审计完整取得。UX、欧美文案质感、市场匹配类结论须标注「待真人验证」，直到完成约定范围的试用。
8. **交叉复核**：P0/P1 级结论（安全、合规、架构）须由另一模型或另一轮独立会话复核。
9. **未检独立於分数**：凡尚未执行检查或证据不足、无法诚实打分的项，标为 **未检**，**不得**记入 0–4 分语义（见第 3.2 节）。模型选择**不写进**本文件。

---

## 2. 审计时点

| 时点 | 深度 | 目的 |
|---|---|---|
| 首次基线审计（距目标发布仍有余量时优先） | 完整（全部 11 个维度，允许大量「未检」） | 建立评分卡与风险登记册，留足整改时间 |
| 每个 PR / 日常 | 自动化检查 | lint、依赖扫描、架构契约、e2e 守门 |
| 每个里程碑结束 | 轻量复审 | 只审变化部分 + P0/P1 整改是否落地 |
| 发布前（若启动发布门禁） | 短审计（1–2 天） | **只**查**一票否决项**与登记过的 P0/P1 是否有关闭证据 |
| 发布后 30 / 90 天 | 数据驱动复审 | 用真实留存、崩溃、反馈补盲区，修订本基准 |
| 事件触发 | 专项审计 | 更换底层模型；改动数据上传/备份逻辑；进入新市场；重大安全或舆情事件；大规模重构后 |

完整审计之后到发布之间应预留足够整改时间；**具体周数取决于已拍板发布日**（未拍板则只写「待排期」）。

## 3. 评分维度与通过线

### 3.1 等级与通过线的含义

**得分等级（仅适用于「已检」项）**：**0** 缺失 / **1** 临时性做法 / **2** 有做法但不稳定 / **3** 稳定可复现 / **4** 有度量且持续改进。

**过线（≥3）在 v1.1 中的含义**：看**结果**，不把「有没有某份文档的名字」当及格条件。

- **架构（维度 1）**：关键决策是否在**现有**权威文档（如 `ARCHITECTURE.md`、`PRINCIPLES.md`、`PROCESS.md`、已合并 PR 说明、工程契约）中可追溯；模块边界与约束是否在代码与自动化检查中可验证。**C4 图、ADR、适应度函数**可作为**可选**表达；若未采用，记「方法未采用」，**不因此单独扣分**。
- **项目管理（维度 4）**：活跃工作是否在任务账（`TASKS.md` / `TEST_TRACKER.md` 等）与 PR / Issue 链路中可追溯；搁置项是否有登记与复盘条件。**DORA 四指标**可作为**可选**观测；未建立仪表时记「未采用」，**不因此单独扣分**。
- **产品功能与场景（维度 5）**：与「六类竞争替代」及 `MVP_PRODUCT_DEFINITION.md` 对照是否自洽；核心场景端到端可完成。**不**把具名竞品的功能清单当必选对标；具名产品仅可作某一类内的**例子**（须标注信息来源与日期）。**差异化仍是待验证假设**，不得写成既定事实。

**未检**：该维度或该检查项尚未执行、或证据不足以诚实地给 0–4 分。报告须列出**未检清单**与**覆盖率**（已检维度数 ÷ 11，或已检检查项数 ÷ 计划检查项总数——须在报告内写明分母）。

**维度 11（风险管理）**：若组织级风险登记册**尚未建立**，状态记 **「未建立」**，**不参与过线判定**，其权重**不参与**归一化分母（见第 3.3 节）。

### 3.2 「未检」与「证据不足」

| 状态 | 含义 | 能否给 0–4 分 |
|---|---|---|
| **已检** | 已按检查项执行并有证据 | 可以 |
| **部分已检** | 同一维度内部分检查项已检 | 可对已检子集打分，并明确未检子集 |
| **未检** | 未执行或证据不足以区分 0 与临时/稳定 | **不可以**（该维度整体或该子项不打分） |
| **假设** | 有推断依据但缺直接证据 | 不打分；须写验证方法 |

**禁止**把「未检」与「2 = 有做法但不稳定」混用。未检就是未检。

### 3.3 加权总分（归一化）

只对 **已检且非「未建立」的维度** 计入分母：

**归一化加权分** = Σ(维度得分 × 权重) ÷ Σ(参与计分的维度权重) ÷ 4 × 100  

其中：参与计分的维度 = 已给出 0–4 分且非维度 11「未建立」的项。

总分仅作**趋势参考**；**判定以「各已检维度是否过线 + 是否触发否决项」为准**（基线轮允许大量未检，总分可能大幅低于「完整体检」）。

## 4. 一票否决项（v1.1 收窄表述）

以下任一项经**证据支持**判定为「未通过」，则**在发布门禁审计中**可判为**阻断对外推广**（基线轮**记录状态与证据**，不输出发布裁决）。**V2** 条文保持 analyst 原意，**未收窄**。

- **V1 · 未经同意的外传**：**用户数据在未经有效同意的情况下离开本机**（上传、同步、分析回传等）。**不包括**仅本地持久化。**用户主动发起的备份寄送**等：须核对是否有清晰说明与确认路径；缺省不得外传。对照 **同意页/设置文案与实际网络请求**（第 0 轮须产出对照证据）。
- **V2 · 危机类话题无可靠安全路由**（未改）：自伤、自杀、对他人的严重伤害意图等危机语义无可靠识别与分流（见 B6）。
- **V3 · 已知可利用且未缓解的高危漏洞**：限于**会进入用户安装产物**、**攻击路径在合理威胁模型下可利用**、且**无有效缓解**的漏洞。仅影响开发机或已隔离工具链的漏洞 → **不降格为否决**，记入风险与整改优先级。
- **V4 · 用户数据无可恢复路径**：**用户数据**因产品缺陷**不可恢复**且**无**备份/导出/迁移路径。下列情形**不构成** V4，但可能构成 **P1 体验风险**（见 B5）：产品升级或改名（如数据目录迁移）导致**界面看起来像「进度清空」**，若实际数据仍在旧路径、且**仅在文档**说明需用户用手动备份恢复——须核对**产品内**是否向用户提示用改名前备份恢复；若仅写在仓库文档、应用内无提示 → **登记为 P1 风险**，**不是**否决项。

## 5. 发现分级

| 级别 | 定义 | 处理要求 |
|---|---|---|
| **P0** | 触发否决项，或造成数据不可逆丢失、安全/合规事故、核心流程对用户不可用 | 阻断对外推广候选；**须**进入任务账/正式队列（由治理登记）；审计会话不代替立项 |
| **P1** | 严重影响核心体验、可维护性或可信度，但有绕行办法 | 须在任务账或豁免说明中有记录 |
| **P2** | 明显不足，不影响核心流程 | 可进入 90 天整改计划 |
| **P3** | 可选优化 | 待办池 |

每条发现标注：**修复成本** S（≤1 天）/ M（≤1 周）/ L（>1 周）；**影响面**（全部用户 / 部分场景 / 内部）。

## 6. 证据要求（所有审计通用）

| 发现类型 | 必须附带的证据 |
|---|---|
| 代码 / 架构 | 文件路径 + 行号；必要时的命令输出 |
| 行为缺陷 | 复现步骤 + 期望 + 实际 |
| UI/UX | 截图（标注 OS、分辨率、主题、语言） |
| 性能 | **引用** `docs/audit/facts/<日期>/` 下原始测量文件 + 方法与环境 |
| 合规/安全 | 数据流说明 + 文件/接口 + 对照条款或标准编号；**法律结论须标「法务确认项」** |
| AI 质量 | 输入样例（脱敏）、输出、模型与版本、评测集或路由证据 |
| 假设 | 标注 `[假设]` + 验证方法 |
| 未检 | 标注 **未检** + 缺什么证据或哪一步未跑 |

## 9. 执行流程

### 第 0 轮 · 否决导向取证（低成本优先）

产出「事实底稿」于 `docs/audit/facts/<日期>/`，**至少**包括：

1. **数据是否离开设备**：网络请求清单或抓包摘要 + 触发条件；与同意文案对照（V1）
2. **备份能否导回 / 迁移是否可恢复**：走查或命令记录（V4 与 P1 体验风险）
3. **依赖与许可证扫描**（V3 输入）
4. **密钥与凭据泄露扫描**：仓库工作副本 + **历史提交**（如 `git log -S`、密钥扫描器输出；**禁止**在报告正文复述密钥原文）
5. **同意页/设置文案与实际网络请求对照**（支撑 V1）
6. **已有危机分流 / 路由相关自动化测试**的运行记录或摘录（支撑 B6 / V2）
7. **（可选）** 宣传站 `marketing-site/` 的 axe / Lighthouse：**仅**用于静态站点，**不**替代桌面练习壳性能

**桌面练习壳**与 **Electron** 路径的冷启动/内存等：**若本轮未测**，在事实底稿目录写 `PERF_NOT_RUN.md` 说明原因 → 维度 8 标 **未检**。

### 第 1 轮 · 分任务审计（当前队列：B5、B6）

- **v1.1 定稿后**：先跑 **B5**、**B6**（含否决项 V1/V3/V4 与 V2 的接口部分）。
- **B1–B3、B4a、B4b**：待 B5/B6 与第 0 轮证据稳定后再开；**七份** Task Brief：`briefs/B1` … `B3`、`B4a`、`B4b`、`B5`、`B6`。

### 第 2 轮 · 汇总与复核

另一模型或独立会话复核 **B5/B6 的 P0/P1**；更新风险登记或「未建立」、未检清单、归一化分。

### 真人验证（不阻断 B5/B6）

试用与母语者走查**只约束** UX / 欧美文案 / 市场类结论；**不**作为 B5/B6 开门前置。

## 10. 方法参考（可选工具箱）

C4、ADR、DORA、OWASP、WCAG、NIST AI RMF 等均为**可选用**方法；采用与否不改变 v1.1 的**过线定义**（见第 3.1 节）。

| 领域 | 方法 / 标准 |
|---|---|
| 整体质量模型 | ISO/IEC 25010 |
| 架构 | C4（可选）；架构决策映射到现有文档 |
| 代码 | 复杂度；依赖与重复 |
| 项目管理 | 任务账；可追溯链路；DORA（可选） |
| 安全 | STRIDE；OWASP ASVS |
| 隐私 | GDPR / CCPA 要点；数据最小化 |
| UX | 启发式；关键路径任务测试 |
| 可访问性 | WCAG 2.2 AA；EAA（法务确认项） |
| AI | OWASP LLM Top 10；NIST AI RMF；红队用例 |
| 风险 | 概率–影响矩阵；FMEA |
