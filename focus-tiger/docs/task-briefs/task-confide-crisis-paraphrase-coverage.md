## 0. 大白话（给拍板用）

现在判断「这句话是不是危机」靠的是一张固定短语表。表里有「kill myself」「自杀」「死にたい」这些。

于是两头都会错，而且**错的方向相反**：

- **漏**：不含表里原词的改写句——「我撑不下去了」「maybe everyone would be better off without me」「もう消えるしかない」——今天一律落到自由生成，由本地模型即兴回应，**而且会被朗读出来**。
- **误**：英文是裸子串匹配，没有词边界也不看否定。「I read an article about suicide prevention today」今天会收到危机资源文案。

这两头不能各修各的：把表扩大到能接住漏的，必然让误的更多；把匹配收紧到不误伤，漏得更多。所以需要先决定**宁可错在哪一边**，再谈怎么实现。

这份稿子不做决定，只把选项和代价摆齐。

## 一、现状（已实测，非推测）

短语表：`confideSafetyKeywords.js`，EN 15 条 / ZH 13 条 / JA 5 条，匹配方式是 `haystack.includes(needle)`。

### 漏的一侧（A-1）

| 输入 | 判为危机？ | 实际路由 | 会被朗读？ |
|---|---|---|---|
| `I want to kill myself` | 是 | `safety_redirect` | 否（纯文字） |
| `I do not see the point of being here anymore` | **否** | `fallback` → 自由生成 | **是** |
| `I want to disappear forever` | **否** | `fallback` → 自由生成 | **是** |
| `maybe everyone would be better off without me` | **否** | `fallback` → 自由生成 | **是** |
| `我撑不下去了` | **否** | `fallback` → 自由生成 | **是** |
| `我不想醒来了` | **否** | `fallback` → 自由生成 | **是** |
| `もう消えるしかない` | **否** | `fallback` → 自由生成 | **是** |

注意 JA 表里有 `消えたい`（想消失），但接不住 `消えるしかない`（只能消失了）——后者语气更重。

上表六条漏接改写句的现状已被 `systemTtsBridge.test.js` 的快照用例钉住，注释写明**钉的是现状不是期望**，改了会红，不会被无声改掉。表中另有一条明确危机基准句，不应计入漏接数量。

### 误的一侧（A-3）

- `I read an article about suicide prevention today` → `safety_redirect`（`suicide` 子串命中）
- `self harm` 会命中 `self harmony`
- `hurt myself` 会命中引述句（「他说他想 hurt myself，我不知道怎么办」这类替人转述）
- ZH `自杀` 会命中「自杀式加班」这类比喻

按 `PRINCIPLES.md`，误伤方向是「对不确定要不要谈的人主动贴心理状态标签」，属明确红线侧。

## 三、要拍板的第一件事：宁可错在哪一边？

这是整份稿子的前置，其余都由它推导。

| 取向 | 含义 | 代价 |
|---|---|---|
| **宁可多接（召回优先）** | 有疑似就给危机资源 | 更多人被贴上「你看起来有危机」的标签，撞 `PRINCIPLES.md` 红线；且危机文案不朗读，正常倾诉者会突然失去语音 |
| **宁可少接（精确优先）** | 只有明确表述才算 | 上表六条漏接改写句继续交给本地模型即兴回应并朗读 |
| **分层**（见第四节） | 明确表述照旧；疑似的既不贴标签也不放任 | 要新增一条产品语义，工作量最大 |

**我的看法**：第三条最合理。前两条是在两种伤害之间二选一，而第三条承认「疑似」本来就是第三种状态，不该被硬塞进现有两个桶。但这需要你先认可「疑似」值得单独存在，否则不必往下做。

### 已拍板（2026-09-30）

**分层，且偏召回。**

- 明确档（原有显式危机词）走完整危机路由，**不变**。
- 疑似档**不进**完整危机路由，也**不按**普通闲聊处理。
- PO 的理由：这六条今天落到 `fallback`，会被模型即兴回应并朗读，对真正处于危机中的人风险更高。所以疑似档**不能只观察不干预**，至少要有一个保守的可见行为。

## 四、要拍板的第二件事：如果走分层，疑似档做什么？

疑似档的候选行为（可组合）：

1. **不自由生成**：不让本地模型即兴回应，改用一条预写的、不贴标签的稳态回应。
2. **不朗读**：与危机路由一致，只出文字。
3. **照常回应但记影子日志**：先只观察，不改用户可见行为——**这是唯一的 A 类选项**，可以不等完整拍板先做，用来攒真实分布。

**我的看法**：先只做第 3 条。现在没有任何数据说明疑似句在真实使用里有多少、长什么样，直接设计可见行为是在猜。影子一段时间后再回来定第 1、2 条。

### 已拍板（2026-09-30）

**三条都做，但分两步上；影子日志可以先行，不等其余拍板。**

- **第一步（A 类，可先做）**：影子日志。只记 `queryHash`、`textLength`、命中的疑似模式 id，**不存原文**——与 K-4 的隐私契约（Issue #1037）同一套写法，直接复用 `buildKbRetrievalMissTurnLog` 里的 FNV-1a。**保留 7 天**，沿用 `turns.jsonl` 的 5 MiB 总上限，且字段明确标为**只用于聚合校准**。
- **第二步（B 类）**：保守可见行为 = **不朗读** + **温和确认句**（替代模型即兴生成）。PO 已拍板要有，但确认句文案本身仍需送审，见第九节。

### A 类实施进度（2026-10-01）

PR #1052 已按六条漏接改写句抽出第一版候选模式并接入本地影子记录。该候选表**只用于观察**，不改变路由、回复、朗读或情绪桶；它不是第二步 B 类生产模式表的自动批准。后续只能用聚合命中分布校准候选，不能从 hash 还原或收集原文。

## 4.5 疑似档与 `sad` 桶的边界（本稿要解决的冲突疑点）

第八节标的冲突疑点是：疑似档与情绪 `sad` 桶会互相抢。**这个冲突可以被取消，而不是被仲裁。**

### 为什么不该排优先级

两者回答的**不是同一个问题**：

| | 回答什么 | 决定什么 |
|---|---|---|
| `sad` 桶 | 这句话的**情绪色调**是什么 | 回复用什么**语气** |
| 疑似档 | 这句话里有没有对**「继续存在」的动摇** | 回复被允许**做什么** |

它们正交，一句话可以同时是两者。而且**疑似句不一定听起来悲伤**：`maybe everyone would be better off without me` 语气是平的、甚至像在替别人着想；`我撑不下去了` 更接近疲惫。若按「谁更像」排序，恰恰是风险最高的那几句会被 `sad`（甚至 `tired`）抢走。

所以排优先级这条路本身就是错的——它假设两者在争同一个位置。

### 已拍板（2026-09-30）：疑似是**标志**，不是桶

疑似档**不参与路由竞争**。路由照旧由现有分类器给出（`sad` / `tired` / `stuck` / `fallback` …），疑似只是挂在旁边的一个 flag；flag 置位时，**无论路由是什么**，施加两条约束：

1. **不朗读**（与危机路由一致）
2. **不自由生成**，改用预写的温和确认句

这与仓库里已有的朗读闸是**同一种形状**：横切约束，不是并列的桶。因为它不占路由位，也就没有什么可仲裁的——冲突消失，而不是被判决。

### 优先级（只有一条，且不涉及情绪桶）

```
明确危机词  >  疑似 flag  >  路由语气
```

- 命中明确危机词 → 走完整危机路由，疑似 flag **不再参与**（不叠加、不重复处理）。
- 未命中明确词但命中疑似模式 → 路由照常算出来，但被上面两条约束罩住。
- 都没命中 → 完全维持现状。

### 一条附带决定：确认句不按情绪分版本

疑似 flag 触发时用**同一条**温和确认句，**不**按 `sad` / `tired` / `fallback` 分版本。理由：按情绪选文案等于把刚拆开的两层重新耦合回去，而且要为每个桶各审一条文案。先保持笨，真有需要再拆。

### 因此第八节的冲突疑点已关闭

原疑点「疑似档与 `sad` 桶职责边界未定」——边界是：**`sad` 决定语气，疑似决定权限，互不覆盖**。已不构成实现阻塞。

## 五、要拍板的第三件事：用什么判，不用什么判

| 手段 | 能不能接住第一节那六条漏接改写句 | 会不会加重 A-3 误伤 | 备注 |
|---|---|---|---|
| 继续扩短语表 | 部分（逐条硬编） | **会**，且每加一条都要人审 | 现注释已写「Expand only with human review」 |
| 给现有匹配加词边界 + 否定检测 | 不能（那是另一头） | **能减轻** | 与扩表正交，可单独做 |
| 用已装的 Qwen3-Embedding 做危机语义近邻 | 能（改写句语义近） | 取决于阈值 | 与知识库近义匹配同一套基建 |
| 交给本地模型判 | 不确定 | 不可控 | 安全判定不应依赖不确定输出 |

**我的看法**：拆成两件独立的事最稳妥。**加词边界 + 否定检测**只收窄误伤、不碰召回，代价小、判定确定、可单独验收，建议先做；**语义近邻接改写句**依赖第三、四节的取向拍板，且要先有影子数据，排在后面。

### 已拍板（2026-09-30）

**拆，且先做。** 已作为独立 PR 先行，用例含「读文章 / 讨论话题 / 否定句」三类。

PO 特别点名的红用例：**否定检测不得把 `不想活了` 这类否定形式的真实危机句误放行**。这条已单独立为红用例——否定检测只处理「否定了危机动词」（`I don't want to hurt myself`），不处理「危机表述本身含否定词」（`不想活`、`don't want to live`），两者形似而语义相反。

疑似模式表走语义近邻还是短语表，**留到影子数据回来后再定**，不在本次范围。
